## 2. Maven Project Structure & Build Artifacts Analysis

### Standard Maven Project Layout
```text
my-maven-project/
├── pom.xml                          # Project Object Model configuration
├── src/
│   ├── main/
│   │   ├── java/                    # Java source code (.java)
│   │   ├── resources/               # Configuration files (config.properties, log4j2.xml)
│   │   └── webapp/                  # Web root (for WAR: WEB-INF/web.xml, JSPs, CSS, JS)
│   └── test/
│       ├── java/                    # Unit & integration test code (JUnit / TestNG)
│       └── resources/               # Test configuration files
└── target/                          # Output generated by Maven builds
    ├── classes/                     # Compiled main .class files & copied resources
    ├── test-classes/                # Compiled test .class files
    ├── surefire-reports/            # Test execution logs (.txt) and results (.xml)
    ├── maven-archiver/              # Archiver properties and manifest metadata
    ├── maven-status/                # Compiler plugin tracking status
    └── my-maven-project-1.0.jar     # Final packaged distributable artifact
```

### Analysis of Your `target/` Directory:
In `C:\Users\fs\eclipse-workspace\my-maven-project\target`:
- **`classes/`**: Contains compiled bytecode (`.class` files) of your application classes from `src/main/java`.
- **`test-classes/`**: Contains compiled test classes from `src/test/java`.
- **`surefire-reports/`**: Contains JUnit test execution results (both summary `.txt` and machine-readable `.xml` reports).
- **`maven-archiver/`**: Contains `pom.properties` with the Maven coordinates and build metadata.
- **`maven-status/`**: Internal compiler tracking files for incremental compilation.
- **`my-maven-project-*.jar`**: The packaged Java Archive ready for execution or distribution.

## 3. Maven Build Lifecycle & Key Goals

```text
clean ──> validate ──> compile ──> test ──> package ──> verify ──> install ──> deploy
```

- **`clean`**: Deletes the `target/` directory and removes all previously compiled artifacts.
- **`compile`**: Compiles source files under `src/main/java` into `target/classes/`.
- **`test`**: Compiles `src/test/java` and executes unit tests using the Surefire plugin.
- **`package`**: Packages compiled code and resources into target artifact format (`.jar` or `.war`).
- **`install`**: Installs the packaged artifact into the local Maven cache (`~/.m2/repository/`).
- **`deploy`**: Uploads the finished artifact to an external remote repository (e.g., Nexus, Artifactory).

## 4. Step-by-Step Lab Setup & Execution Guide

### Part A: Creating a Maven Java Project (CLI & Eclipse)
1. **Using Command Line:**
   ```bash
   mvn archetype:generate \
     -DgroupId=com.example \
     -DartifactId=my-maven-project \
     -DarchetypeArtifactId=maven-archetype-quickstart \
     -DarchetypeVersion=1.4 \
     -DinteractiveMode=false
   ```
2. **In Eclipse IDE:**
   - Go to **File $\rightarrow$ New $\rightarrow$ Project...**
   - Expand **Maven** $\rightarrow$ select **Maven Project** $\rightarrow$ click **Next**.
   - Select Archetype: `org.apache.maven.archetypes:maven-archetype-quickstart`.
   - Enter **Group Id** (e.g., `com.example`) and **Artifact Id** (e.g., `my-maven-project`).
   - Click **Finish**.

3. **Building & Running:**
   ```bash
   cd my-maven-project
   mvn clean install
   java -cp "target/my-maven-project-*.jar" com.example.App
   ```

---

### Part B: Creating a Maven Web Java Project (WAR & Tomcat)
1. **Using Command Line:**
   ```bash
   mvn archetype:generate \
     -DgroupId=com.example \
     -DartifactId=my-web-app \
     -DarchetypeArtifactId=maven-archetype-webapp \
     -DarchetypeVersion=1.4 \
     -DinteractiveMode=false
   ```
2. **Adding Servlet & JSTL Dependencies in `pom.xml`:**
   ```xml
   <dependencies>
       <!-- Servlet API (provided by container) -->
       <dependency>
           <groupId>javax.servlet</groupId>
           <artifactId>javax.servlet-api</artifactId>
           <version>4.0.1</version>
           <scope>provided</scope>
       </dependency>

       <!-- JSTL for Dynamic Views -->
       <dependency>
           <groupId>javax.servlet</groupId>
           <artifactId>jstl</artifactId>
           <version>1.2</version>
           <scope>compile</scope>
       </dependency>
   </dependencies>
   ```

3. **Configuring Tomcat in Eclipse:**
   - Open **Window $\rightarrow$ Show View $\rightarrow$ Servers**.
   - Click **Add Server** $\rightarrow$ select **Apache Tomcat v9.0** (or corresponding version) $\rightarrow$ point to Tomcat installation directory.
   - Right-click server $\rightarrow$ **Add and Remove...** $\rightarrow$ add `my-web-app` $\rightarrow$ Start Server.
   - Open browser: `http://localhost:8080/my-web-app/`.

### Part C: Essential Configurations in `pom.xml`

#### 1. Java Compiler Configuration (Java 17)
```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.11.0</version>
            <configuration>
                <release>17</release>
            </configuration>
        </plugin>
    </plugins>
</build>
```

#### 2. Executable Standalone JAR Configuration
```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-jar-plugin</artifactId>
    <version>3.3.0</version>
    <configuration>
        <archive>
            <manifest>
                <addClasspath>true</addClasspath>
                <mainClass>com.example.App</mainClass>
            </manifest>
        </archive>
    </configuration>
</plugin>
```

#### 3. Reading Resource Files (`src/main/resources/config.properties`)
```java
try (InputStream input = getClass().getClassLoader().getResourceAsStream("config.properties")) {
    Properties prop = new Properties();
    if (input == null) {
        System.out.println("Unable to find config.properties");
        return;
    }
    prop.load(input);
    System.out.println("Property value: " + prop.getProperty("app.name"));
}
```

## 5. Scenario-Based Questions & Complete Solutions

### Q1: Resolving Compiler Plugin Failures via Terminal
**Problem:** Error `Failed to execute goal org.apache.maven.plugins:maven-compiler-plugin:3.8.1:compile ... Re-run Maven with the -X switch.` How to resolve using terminal?

**Solution:**
1. Execute Maven with debug and stacktrace flags:
   ```bash
   mvn clean compile -X -e
   ```
2. **Review Diagnostic Logs:**
   - **Java Version Incompatibility:** Verify if JDK version matches compiler configuration (`mvn -version`). Update `<release>17</release>` or `<source>17</source><target>17</target>` in `pom.xml`.
   - **Corrupted Local Dependencies:** Force refresh via `mvn clean compile -U`.
   - **Syntax Errors:** Examine compiler messages immediately preceding the `[ERROR]` block to identify line-specific errors in `src/main/java`.

### Q2: Dependency Not Recognized by Compiler
**Problem:** A dependency added to `pom.xml` is not recognized. What steps confirm its presence in `.m2` and dependency tree?

**Solution:**
1. **Analyze Dependency Tree:**
   ```bash
   mvn dependency:tree
   ```
2. **Inspect Local Repository (`.m2`):**
   - Path (Windows): `%USERPROFILE%\.m2\repository\<group_path>\<artifactId>\<version>\`
   - Path (Linux/Mac): `~/.m2/repository/<group_path>/<artifactId>/<version>/`
   - Check if `.jar` exists and verify it is not empty (0 KB) or accompanied by `.lastUpdated` error files.
3. **Purge and Re-download:**
   ```bash
   mvn dependency:purge-local-repository
   mvn clean compile -U
   ```
4. **Eclipse IDE Refresh:**
   Right-click project $\rightarrow$ **Maven $\rightarrow$ Update Project...** (or `Alt + F5`) $\rightarrow$ check **Force Update of Snapshots/Releases** $\rightarrow$ click **OK**.

### Q3: Applying a `.patch` File in a Maven Build
**Problem:** A teammate sends a `.patch` file for a bug fix. How to apply it and include it in your build?

**Solution:**
1. **Test the patch before applying:**

   git apply --check bugfix.patch

2. **Apply the patch:**

   - Via patch tool: `patch -p1 < bugfix.patch`
   - In Eclipse: Right-click project $\rightarrow$ **Team $\rightarrow$ Apply Patch...** $\rightarrow$ select file $\rightarrow$ **Finish**.
3. **Verify and build with Maven:**
   ```bash
   mvn clean test
   mvn clean install
   ```

### Q4: Rerunning Only Failed JUnit Tests
**Problem:** Multiple JUnit tests failed. How to rerun only the failing tests?

### Q5: Fixing "Unsupported Class Version Error"
**Problem:** Build fails with `UnsupportedClassVersionError`. What plugin and configuration to review?

**Solution:**
- **Plugin to Review:** `maven-compiler-plugin`.
- **Root Cause:** Bytecode version mismatch (e.g., compiled with Java 17 [class version 61], but runtime environment uses Java 11 [class version 55]).
- **Fix in `pom.xml`:**
  ```xml
  <properties>
      <maven.compiler.source>17</maven.compiler.source>
      <maven.compiler.target>17</maven.compiler.target>
  </properties>
  ```
- **Environment Checks:**
  - Check Maven CLI Java: `mvn -version`.
  - Check Eclipse JRE: **Window $\rightarrow$ Preferences $\rightarrow$ Java $\rightarrow$ Installed JREs**.

### Q6: Converting a WAR Project to a Standalone Executable JAR
**Problem:** Converting an application from WAR to standalone executable JAR.

**Solution:**
1. Change packaging in `pom.xml`:
   ```xml
   <packaging>jar</packaging>
   ```
2. Replace `maven-war-plugin` with `maven-jar-plugin` (or `maven-shade-plugin` / `spring-boot-maven-plugin`):
   ```xml
   <plugin>
       <groupId>org.apache.maven.plugins</groupId>
       <artifactId>maven-jar-plugin</artifactId>
       <version>3.3.0</version>
       <configuration>
           <archive>
               <manifest>
                   <addClasspath>true</addClasspath>
                   <mainClass>com.example.MainApp</mainClass>
               </manifest>
           </archive>
       </configuration>
   </plugin>
   ```
3. Remove or replace `<scope>provided</scope>` servlet dependencies with embedded containers if web capability is required.
4. Move web resources from `src/main/webapp/` to `src/main/resources/`.

### Q11: Maven Dependency Conflict Resolution Strategy
**Problem:** How Maven resolves dependency conflicts and how to manage the dependency tree.

**Solution:**
- **Resolution Strategy ("Nearest Wins" / Dependency Mediation):**
  1. **Tree Depth:** The dependency version closest to the root project in the hierarchy takes precedence.
  2. **First Declaration Rule:** If two conflicting dependencies exist at identical tree depth, the first declared in `pom.xml` wins.
- **Viewing Dependency Tree:**
  ```bash
  mvn dependency:tree -Dverbose
  ```
- **Overriding Conflicts:**
  1. Directly declare the desired version in `<dependencies>`.
  2. Use `<exclusions>` to suppress unwanted transitive artifacts.
  3. Manage global module versions via `<dependencyManagement>`.

### Q13: Creating an Executable JAR with a Main Method
**Problem:** Creating an executable JAR and configuring its plugin.

**Solution:**
- **Option 1: Thin JAR (`maven-jar-plugin`)**
  ```xml
  <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-jar-plugin</artifactId>
      <version>3.3.0</version>
      <configuration>
          <archive>
              <manifest>
                  <addClasspath>true</addClasspath>
                  <mainClass>com.example.Main</mainClass>
              </manifest>
          </archive>
      </configuration>
  </plugin>
  ```
- **Option 2: Fat/Uber JAR with Dependencies (`maven-shade-plugin`)**
  ```xml
  <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-shade-plugin</artifactId>
      <version>3.5.0</version>
      <executions>
          <execution>
              <phase>package</phase>
              <goals><goal>shade</goal></goals>
              <configuration>
                  <transformers>
                      <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                          <mainClass>com.example.Main</mainClass>
                      </transformer>
                  </transformers>
              </configuration>
          </execution>
      </executions>
  </plugin>
  ```
- **Execution:** `java -jar target/myapp.jar`

### Q17: JSTL, Servlet API, and Rationale for `provided` Scope
**Problem:** Adding JSTL and Servlet API dependencies, and why Servlet API uses `provided` scope.

**Solution:**
- **`pom.xml` Configuration:**
  ```xml
  <dependencies>
      <dependency>
          <groupId>javax.servlet</groupId>
          <artifactId>javax.servlet-api</artifactId>
          <version>4.0.1</version>
          <scope>provided</scope>
      </dependency>
      <dependency>
          <groupId>javax.servlet</groupId>
          <artifactId>jstl</artifactId>
          <version>1.2</version>
          <scope>compile</scope>
      </dependency>
  </dependencies>
  ```
- **Why `provided` Scope?**
  1. Apache Tomcat bundles its own `servlet-api.jar` in its `/lib` folder.
  2. If bundled into `WEB-INF/lib/` inside the WAR, conflicting classloader hierarchies cause `ClassCastException` and `LinkageError`.
  3. `provided` allows compilation and test execution while omitting the library from the final packaged WAR.

### Q18: Multi-Module Maven Web Project Architecture
**Problem:** Setting up a multi-module Maven project with core and web submodules.

**Solution:**
1. **Project Directory Layout:**
   ```text
   parent-project/
   ├── pom.xml                 # packaging = pom
   ├── core-module/            # packaging = jar (Business Logic / Entities)
   │   └── pom.xml
   └── web-module/             # packaging = war (Servlets / JSPs / Controllers)
       └── pom.xml
   ```
2. **Parent `pom.xml`:**
   ```xml
   <groupId>com.example</groupId>
   <artifactId>parent-project</artifactId>
   <version>1.0.0</version>
   <packaging>pom</packaging>
   <modules>
       <module>core-module</module>
       <module>web-module</module>
   </modules>
   ```
3. **Web Module Dependency on Core (`web-module/pom.xml`):**
   ```xml
   <dependencies>
       <dependency>
           <groupId>com.example</groupId>
           <artifactId>core-module</artifactId>
           <version>${project.version}</version>
       </dependency>
   </dependencies>
   ```
4. **Build:** Run `mvn clean install` from the `parent-project/` root. Maven builds `core-module.jar` first, then packages it into `web-module.war/WEB-INF/lib/`.

### Q19: Traditional WAR Web Projects vs Standalone Modern Applications
**Problem:** Comparison between traditional WAR-based projects and standalone executable JARs.

| Dimension | Traditional WAR Web Application | Modern Standalone Executable (Spring Boot / Fat JAR) |
| :--- | :--- | :--- |
| **Packaging** | `<packaging>war</packaging>` | `<packaging>jar</packaging>` |
| **Servlet Container** | External standalone container (Tomcat / WildFly) | Embedded container inside application (Tomcat / Jetty) |
| **Execution** | Deployed into container `/webapps` directory | Run directly via CLI: `java -jar app.jar` |
| **Configuration** | `WEB-INF/web.xml` deployment descriptor | Code-based `@Configuration` & `application.properties` |
| **Port & Networking** | Configured in server `server.xml` | Configured in application properties (`server.port=8080`) |
| **Containerization** | Requires heavyweight multi-step container image | Lightweight, cloud-native containerized execution |
